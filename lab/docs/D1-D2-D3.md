# Evidências e critérios para D1, D2 e D3

Este roteiro complementa as entregas da equipe. Não contém resultados de execução fictícios.

## D1 — plano de teste

**Escopo:** Loja Potengi, projeto Docker `lab91`, rede local do lab, dois nós PostgreSQL, HAProxy, MinIO e gerador. RTO alvo de 30 min e RPO alvo de 5 min. Papel dos membros e autorização do exercício devem ser preenchidos pela equipe.

**Pré-condições:** `check.sh` aprovado; um `BACKUP_OK`; um `RESTORE_OK`; capacidade de disco verificada; nenhum incidente concorrente; relógio do host correto; imagens previamente construídas; pasta `runtime` preservada. O teste de retorno inseguro pressupõe failover concluído. Não execute os testes contra produção.

### Gates antes dos incidentes

```bash
./lab.sh subir
```

Após a subida indicada no README:

```bash
./lab.sh checar
./lab.sh validar
./lab.sh testar-backup
```

Não avance se algum comando retornar código diferente de zero. Confirme que `archive-init` e `minio-test` terminaram com exit code 0. Confirme os health checks do proxy e do backup. O health check do banco verifica disponibilidade do processo, enquanto `check.sh` verifica os papéis de escritor e standby.

| Caso | Incidente | Recuperação | Critério de aceite |
|---|---|---|---|
| T1 — failover | Parar o escritor original. | Executar `failover.sh --aceitar-perda-potencial`. | Antes da promoção: nenhuma escrita enviada ao standby. Após isolamento e promoção: escrita pelo proxy e gerador retomados. RTO e perda efetiva medidos. |
| T2 — retorno antigo | Após T1, iniciar novamente o nó antigo pelo Compose corrigido. | Confirmar bloqueio; depois executar `rejoin.sh` com aceite de descarte. | Nenhum desvio do tráfego para o nó antigo. Reclone termina em standby e streaming; escritor continua o promovido. |
| T3 — restauração remota | Considerar os arquivos locais indisponíveis; não usá-los no restore. | `restore-test.sh`, sem apagar volumes. | Dump e roles baixados por versão do MinIO; hashes corretos; `pg_restore` sem erro; tabela e dados consultáveis. |
| T4 — falha de backup | Parar o MinIO em janela controlada. | Reativar o MinIO e aguardar novo conjunto completo. | Falha de upload não registra `BACKUP_OK`; último sucesso é preservado. Sem novo backup por mais de 300 s, health check fica unhealthy. Depois da recuperação, novo conjunto validado e restore aprovado. |

T3 demonstra independência lógica da cópia local: o código de restauração consulta exclusivamente S3. Não é necessário apagar o volume de backups para provar isso. Caso o exercício exija destruição física da cópia local, esse incidente deve ser planejado separadamente, com as proteções exigidas pelo instrutor.

**Critérios de parada:** isolamento do escritor não confirmável; dois bancos graváveis sem autorização clara; inconsistência de WAL; backup remoto não validado; ausência de espaço seguro; erro de restauração. Interromper o gerador e preservar logs antes de improvisar correções.

## D2 — registro de execução

Use uma pasta de evidências por rodada. Os scripts de failover e restore já criam logs com data/hora; registre também o instante real do incidente.

| Campo | Preencher no lab |
|---|---|
| Execução / responsáveis | — |
| Caso / hipótese | — |
| Data/hora e fuso | — |
| T0: indisponibilidade real | — |
| Td: detecção | — |
| Ta: início da recuperação | — |
| Tw: primeira escrita válida após a recuperação | — |
| Tb: redundância restabelecida | — |
| Último pedido confirmado antes da falha | ID e `criado` |
| Último pedido recuperado | ID e `criado` |
| Conjunto de backup e versões | `id`, manifesto, versões |
| RTO observado | `Tw - T0` |
| MTTD observado nesta execução | `Td - T0` |
| Perda temporal observada | Comparação entre os pedidos confirmados e recuperados |
| Aprovação / reprovação | Conforme os critérios, não apenas pela cor do monitor |
| Evidências | Logs, consultas, prints e códigos de retorno |

**Como medir RPO sem confundir atraso e recuperação:** registre o último pedido confirmado antes da falha, fora do banco afetado, e compare com o histórico recuperado. O intervalo de 5 s do gerador introduz granularidade na medição. `now() - max(criado)` também cresce quando o gerador está parado; esse valor sozinho não prova perda de dados. `pg_last_xact_replay_timestamp()` fica antigo num banco ocioso e tampouco é prova suficiente de atraso.

**RTO:** a linha `T_ESCRITA` do failover comprova uma escrita de teste pelo proxy, mas registre também a retomada do gerador e os critérios de negócio. Uma promoção em poucos segundos não demonstra, por si só, que o RTO do incidente inteiro foi cumprido. O retorno da redundância pode ocorrer depois da retomada do serviço; registre os dois tempos separadamente.

Consultas úteis para evidência:

```sql
SELECT pg_is_in_recovery();
SELECT id, criado FROM pedidos ORDER BY id DESC LIMIT 10;
SELECT status, sender_host, received_tli, latest_end_lsn FROM pg_stat_wal_receiver;
SELECT application_name, state, sent_lsn, write_lsn, flush_lsn, replay_lsn FROM pg_stat_replication;
SELECT archived_count, failed_count, last_archived_time, last_failed_time FROM pg_stat_archiver;
```

## D3 — avaliação e plano de melhoria

| Gap | Implementação entregue | Evidência exigida para encerrar | Situação antes da execução integrada |
|---|---|---|---|
| Retorno inseguro / split-brain | Autorização persistente, bloqueio no launcher, rejoin com clone. | T2 aprovado, apenas um escritor, standby em streaming. | Implementado; pendente homologação. |
| Failover não recupera escrita | Check SQL e promoção após isolamento. | T1 aprovado; RTO/RPO dentro dos limites ou desvio explicitado. | Implementado; pendente homologação. |
| Backup imutável ausente | Upload com lock, versões e SHA-256; restore isolado. | Inicialização de retenção, T3 e T4 aprovados; RPO medido. | Implementado; pendente homologação. |
| Disco e domínio de falha | Retenção local curta e rotação de logs, sem solução integral. | Capacidade/quota, política segura de WAL e cópia fora do host. | Aberto — alta prioridade. |
| PITR | Não implementado. | Backup físico base + WAL + recuperação por horário testada. | Aberto. |
| Alertas e cobertura de monitoramento | Checks de papel SQL e idade de backup. | Alertas internos, lag, disco e arquivamento monitorados. | Parcial. |
